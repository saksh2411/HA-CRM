## SRS ambiguities and authorized implementation decisions

- The SRS says “zero-latency” and sub-100 ms query execution without workload, hardware, or percentile definitions. These are performance goals, not verifiable guarantees. Pagination/indexing are implemented; measurement requires the target host and representative data.
- “Online sales reps” has no presence service definition. As authorized, recipients are active eligible Sales Reps in the tenant, round-robin assigned.
- Lead-source ROI has no acquisition-cost source or exact formula. A nullable lead source cost is stored; ROI is `(won revenue - acquisition cost) / acquisition cost` where cost is available, otherwise ROI is null.
- Invoice/tax legal format, tax jurisdiction, rounding scope, and currencies' exchange rates are unspecified. Generic percentage tax and INR/USD/EUR/GBP without conversion are used; line/global discounts and totals use the approved DECIMAL calculation order and two-decimal rounding.
- Deal “net value” could mean amount minus discount or amount less discount plus tax. The implementation stores amount less discount plus percentage tax; the pipeline display currently uses amount, so confirm desired reporting interpretation before calling totals equivalent.
- SRS sample SQL uses global unique user email and a destructive cascade from contact to deal. This project follows approved requirements instead: tenant-scoped unique email and SET NULL/retention to preserve sales history.
- SRS lists PHP 8.1/8.2; the approved architecture requires PHP 8.2+.
- SRS says native HTML/CSS/vanilla ES6/Axios/DataTables and mentions Bootstrap/Tailwind CDN; the approved React requirement overrides that client-stack description. React/Vite is compiled to static files, with no Node runtime.
- SRS calls notifications “Long-Polling/AJAX”; the implementation uses bounded 20-second AJAX polling, not a blocking long-poll, to fit shared hosting and the explicit no-WebSocket decision.
- Shared hosting can differ on Apache rewrite, filesystem paths, `open_basedir`, SSL, PHP extensions, MySQL SQL modes and cron availability. README documents the required setup; real host validation remains necessary.

1. Complete the form/UI gaps explicitly marked Partial above, especially full lead filters/fields, multi-line billing edit, richer contacts/accounts details, support response workflows, and dashboard/report filtering.
2. Validate on MariaDB 10.5+ or MySQL 8.0; this XAMPP installation provides MariaDB 10.4.32. Add durable automated tests for permission matrices, billing edge cases, SMTP transport with a safe mail sink, cron concurrency, and broader CRUD coverage.
3. Test installation on a representative cPanel/shared-hosting account. XAMPP Apache configuration was checked but Apache itself was not started in this run.
